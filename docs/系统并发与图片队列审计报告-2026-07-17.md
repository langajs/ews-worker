# EWS SaaS 并发与图片队列审计报告

> 归档仓库：`ews-worker`
> 审计版本：2026-07-22 / v1.2（单跳 Queue、R2 直传与浏览器 SKU 转码实施版）
> 审计范围：Cloudflare Worker、D1、R2、回调与图片处理队列、n8n 执行层、Shopee/JST 图片任务模型
> 代码基线：`ews-worker/src/index.js`、`ews-worker/src/db.js`、`ews-worker/wrangler.toml` 及当前运行中的 `n8n` Docker 容器
> 结论口径：并发指“同时在途的外部 AI 图片工作流”，不等同于“同时执行 PNG 解码和 JPEG 编码的数量”
> 基线说明：第 3 节起保留 v1.0 改造前发现作为决策记录；以下“实施状态”是当前代码与线上部署口径。

---

## 0. 实施状态

| 项目 | v1.1 当前状态 |
|---|---|
| 回调接入 | `POST /api/callback` 鉴权后直接写原生 Cloudflare Queue `ews-callback-events`，仅在 `send()` 成功后返回 `queued:true`；超过 48KB 的元数据正文暂存 R2 inbox，Queue 只传 key |
| 消费策略 | 单跳消费，`batch_size=1`、`max_concurrency=20`、最多 5 次重试，失败进入 `ews-callback-events-dlq` |
| 图片处理 | AI 回调图片由 n8n 内网 sidecar 使用 `sharp/libvips` 输出 quality 88 JPEG；浏览器 `sku-upload` 自上传成品图在本地逐张转码和必要的等比缩小，Worker 只校验最终 JPG 并写 R2 |
| R2 上传 | sidecar 复用 `callback_secret` 请求 5 分钟单对象 presigned PUT，图片直传 R2；回调只发送 `r2_key` 和校验元数据 |
| R2 校验 | Queue consumer 通过 R2 binding 校验图片对象路径、size、Content-Type、`plan_id` 和 SHA-256 后写业务表；大回调 inbox 在成功或最终失败后删除 |
| D1 旧队列 | `ews_callback_queue`、`ews_image_queue` 仅保留存量兼容和排空逻辑，新回调不再写入 |
| 部署状态 | Worker Queue 和 sidecar 已部署；7 个新版图片工作流需在 R2 S3 Worker secrets 配置后切换 |

本方案不向工作流推送体增加 S3 字段，不向 n8n 暴露长期 R2 凭据，也不传 Base64。R2 S3 Access Key 仅保存在 Worker secret 中。

## 1. 执行摘要

1. 当前系统可以通过架构调整支持 100～200 个图片工作流同时在途，但不能在一个 Worker invocation 内同时转码 100～200 张图片。
2. 当前代码没有使用原生 Cloudflare Queues。`wrangler.toml` 只有 D1、R2 和每分钟 Cron，`ews_callback_queue`、`ews_image_queue` 都是 D1 表。
3. 当前图片回调经过 D1 callback queue 和 D1 image queue 两层，成功图片至少需要多次 D1 状态写入；这套实现可以兜底，但不适合作为 SaaS 的高频消息总线。
4. 当前图片消费者动态并发为 4～12，回调消费者并发为 3。图片转换使用 `pngjs`、`jpeg-js` 和纯 JavaScript Bilinear，Shopee 主图/附图 PNG 固定按质量 88 转 JPG。
5. 当前 n8n 为单个 `n8nio/n8n:stable` 容器，未配置 `DB_TYPE` 和 `EXECUTIONS_MODE`，即默认 SQLite + regular mode，不适合作为 100～200 并发的可靠执行层。
6. Cloudflare Queues 免费版每天包含 10,000 operations。单跳成功消息通常消耗 3 operations，因此理论上限为 3,333 条图片消息/天；按当前两跳结构照搬则只有 1,666 张图/天。
7. 为预留元数据消息、重试和 DLQ，推荐免费版按单跳 2,000～2,500 张生成图片/天设计；若保持两跳则只按 1,000～1,200 张/天设计。
8. 2026-07-22 已移除 Worker 内 `@jsquash` 转码；用户 SKU 图在浏览器处理，AI 图片由 sidecar 处理，因此 Workers Free 不再承担 PNG/JPEG 编解码 CPU。

## 2. 当前技术栈

| 层级 | 当前实现 | 审计判断 |
|---|---|---|
| 前端 | Cloudflare Pages，静态 HTML/JS/CSS | 可继续使用，不是并发瓶颈 |
| API | 单体 Cloudflare Worker | API 吞吐足够，但控制面和图片数据面耦合 |
| 业务状态 | Cloudflare D1 | 适合任务、计数器和幂等状态，不适合高频轮询队列 |
| 对象存储 | Cloudflare R2 binding | 适合最终图片和 staging 图片 |
| 回调队列 | `ews_callback_queue` D1 表 | 非 Cloudflare Queues，消费者并发 3 |
| 图片队列 | `ews_image_queue` D1 表 | 非 Cloudflare Queues，动态并发 4～12 |
| 队列唤醒 | `ctx.waitUntil()` + 每分钟 Cron | 可恢复，但存在 30 秒生命周期和分钟级兜底延迟 |
| 图片算法 | 用户 SKU 图由浏览器逐张转 JPG；AI 图由 sidecar `sharp/libvips` 转码 | Worker 不再执行图片编解码，Free/Paid 均不受此 CPU 风险影响 |
| 工作流 | 单容器 n8n + 默认 SQLite | 当前扩容的主要阻塞点 |

当前关键常量：

- `CALLBACK_QUEUE_BATCH_SIZE = 3`
- `CALLBACK_QUEUE_MAX_ACTIVE = 3`
- `CALLBACK_QUEUE_MAX_ATTEMPTS = 5`
- `MIN_IMAGE_QUEUE_ACTIVE = 4`
- `MAX_IMAGE_QUEUE_ACTIVE = 12`
- `IMAGE_QUEUE_MAX_ATTEMPTS = 5`
- 图片 `processing` 超过 2 分钟会回收，最多重试 5 次
- 推送调度每轮最多处理 100 个计划，每个用户每轮最多取 10 个
- 单用户图片工作流默认最多 20 个在途任务

## 3. 主要审计发现

### P0：当前系统尚未使用 Cloudflare Queues

`ews-worker/wrangler.toml` 没有 Queue producer/consumer binding，也没有 Worker 的 `queue()` handler。当前 Cloudflare Queues 免费额度实际消耗为 0，所有回调排队和图片排队都落在 D1。

影响：

- D1 同时承担业务数据库、回调 inbox、图片队列和调度锁。
- 每张成功图片会经历 callback insert/claim/delete、image insert/claim/delete、图片记录和推送计划状态等多次写入。
- 多任务同时回调时，D1 写入放大和队列状态扫描会先于 R2 成为瓶颈。

### P0：Workers Free 无法承载 Worker 图片转码（已解决）

Cloudflare Workers Free 单次 invocation 只有 10ms CPU，而当前 1K PNG 的解码、透明通道合成和 JPEG 编码属于秒级 CPU 工作。即使 Queue 能接收 3,333 条消息，消费者仍会因 CPU 超限而失败。

2026-07-22 实施状态：浏览器自上传 SKU 图已改为本地逐张转码，Worker WASM 及 `@jsquash` 依赖已删除；AI 图片继续由 sidecar 处理。以下两种方案保留为历史决策依据。

免费栈只有以下两种可行方式：

1. AI/n8n 在回调前已经输出合规 JPG，Worker 只做流式 R2 中继。
2. 图片转换移到 n8n 附近的原生 `sharp/libvips` 服务，Worker 只处理队列和状态。

如果保留当前纯 Worker 转码，则需要 Workers Paid。

### P1：图片回调存在不必要的两跳排队

当前图片回调先进入 callback queue；callback consumer 解析后再写 image queue。迁移到 Cloudflare Queues 时不应原样复制两跳，而应在 callback Worker 完成密钥、任务 ID 和基础 schema 校验后，直接把图片事件发送到 image callback queue。

推荐路径：

```text
n8n/AI -> callback Worker -> image-callback Queue -> R2/转码/D1
                        \-> metadata Queue       -> D1
```

每个回调只进入一个 Queue，图片消息从 6 operations 降到通常 3 operations。

### P1：图片响应体没有完整下载超时

当前 15 秒 AbortController 只覆盖 `fetch()` 返回响应头之前的阶段。读取 `response.body` 时没有独立 idle/total timeout；上游持续建立连接但不结束响应体时，图片消费者仍可能长时间占用执行槽位。

目标实现需要同时具备：

- connect/header timeout
- body idle timeout
- total download timeout
- 最大源文件 16MB 限制
- Queue visibility/重试由平台管理

### P1：单 invocation 批量图片转换存在 128MB 风险

当前 image queue 可一次 `Promise.allSettled()` 处理最多 12 条。1K RGBA 解码后单张像素数据约 4MB，还会同时存在 PNG buffer、JPEG buffer、缩放 buffer 和 JS 对象。Paid Workers 仍只有 128MB 内存，因此 12 张同时解码不安全。

Cloudflare Queue consumer 应设置：

- `batch_size = 1`，最多 2
- 纯 Worker 转码 `max_concurrency = 4～8`
- 每个 Queue invocation 只转换一张图片

### P1：n8n 单容器 SQLite 不能作为 SaaS 执行层

当前 n8n 容器未配置 `DB_TYPE` 和 `EXECUTIONS_MODE`。目标架构需要 PostgreSQL 13+、Redis、queue mode、1 个 main 和 2～4 个 worker。n8n 官方也明确不支持 SQLite 的分布式 queue mode。

官方来源：[n8n Configuring queue mode](https://docs.n8n.io/hosting/scaling/queue-mode/)

## 4. Cloudflare Queues 免费额度

根据 Cloudflare 2026-04-21 更新的官方文档：

- Workers Free：每天包含 10,000 standard operations
- 每个小于 64KB 的成功消息通常产生 3 次操作：write、read、delete
- 每次 retry 额外产生 1 次 read operation
- 每条 Queue 吞吐上限 5,000 messages/s
- 最多 250 个 push consumer invocations
- Free 消息保留时间固定为 24 小时
- operations 按消息而不是 batch 计费

官方来源：

- [Cloudflare Queues Pricing](https://developers.cloudflare.com/queues/platform/pricing/)
- [Cloudflare Queues Limits](https://developers.cloudflare.com/queues/platform/limits/)
- [Cloudflare Workers Limits](https://developers.cloudflare.com/workers/platform/limits/)

### 4.1 单跳图片事件

```text
10,000 / 3 = 3,333 条成功图片消息/天
```

这是没有任何重试、元数据消息和 DLQ 的理论上限。

推荐运营预算：

| 项目 | 每日预算 |
|---|---:|
| 生成图片消息 | 2,000～2,500 |
| 元数据及其他回调 | 300～800 |
| retry、DLQ 和突发余量 | 1,700～3,700 operations |
| 告警阈值 | 8,000 operations |
| 停止继续放量阈值 | 9,000 operations |

### 4.2 按当前两跳结构迁移

每张图片经过 callback Queue 和 image Queue：

```text
2 条消息 × 3 operations = 6 operations/图片
10,000 / 6 = 1,666 张图片/天
```

考虑重试和元数据后，只适合按 1,000～1,200 张图片/天运行。因此不建议保留两跳。

### 4.3 大消息对额度的影响

Queue 每 64KB 算一个 operation 单位。图片二进制不能进入 Queue，只允许传：

- `event_id`
- `task_id`
- `plan_id`
- `sub_task_id`
- `image_type`
- `image_position`
- `source_url` 或 `r2_staging_key`

Shopee/JST 聚合 metadata 回调可能超过 64KB。应先把完整 payload 存入 R2/D1 inbox，再让 Queue 只传 payload key；否则一次 metadata 消息会按多个 64KB 分片重复计费。

## 5. 当前任务模型的图片数量换算

### 5.1 Shopee

定义：

- `S`：生成套数
- `G`：需要 AI SKU 图的一级规格组数
- 主图/附图固定为 9 张，即 1 张封面图 + 8 张附图
- 详情图当前为 0，不进入 Shopee 图片工作流

当前代码生成数量：

| 模式 | AI 图片数量 |
|---|---:|
| full + SKU 自上传 | `9 × S` |
| full + SKU AI | `(9 + G) × S` |
| dedup + SKU 自上传 | `S + 8` |
| dedup + SKU AI | `S + 8 + G` |

dedup 模式为每套生成自己的主图；8 张附图和 AI SKU 图只为第 1 套生成，后续套数在导出时复用。

按单跳安全预算 2,000～2,500 张/天换算：

| Shopee 场景 | 每套/每任务图片量 | 免费 Queues 建议日处理量 |
|---|---:|---:|
| full，SKU 自上传 | 9 张/套 | 222～277 套/天 |
| full，5 个 AI SKU 规格组 | 14 张/套 | 142～178 套/天 |
| 20 套 full，5 个 AI SKU 规格组 | 280 张/母任务 | 7～8 个母任务/天 |
| 20 套 dedup，5 个 AI SKU 规格组 | 33 张/母任务 | 60～75 个母任务/天 |

Shopee 商品 metadata 每个母任务还会增加 1 条非图片回调消息，因此实际可用量应略低于表中上限。

### 5.2 JST

定义：

- `M`：每套主图总量，包含第 1 张主图和后续主图
- `D`：每套详情图数量
- `G`：AI SKU 一级规格组数

当前代码生成数量：

| 模式 | AI 图片数量 |
|---|---:|
| full | `(M + D + G) × S` |
| dedup | `S + (M - 1) + D + G` |

JST metadata 每批最多 10 个商品，同时最多包含 100 个 SKU 标题。metadata Queue 消息应单独计入每日 operation 预算。

## 6. 当前系统能力评估

### 6.1 不改架构

| 能力 | 当前判断 |
|---|---|
| 回调突发接入 | Worker 入口可接收，但 D1 callback consumer 只并发 3 |
| 图片处理 | 动态并发 4～12，但同 invocation 批量转码有内存风险 |
| 外部 AI 在途 | 单用户默认 20；缺少可靠的全局 n8n 容量反馈 |
| 多租户公平性 | 推送层已有按用户轮转，但回调和图片队列仍是共享 FIFO |
| 100～200 在途工作流 | 可以创建，不适合承诺稳定 SLA |
| 日图片 SLA | 未完成正式压测前不能承诺；建议保护值不超过 1,000 张/天 |

当前保护值 1,000 张/天不是算法理论上限，而是考虑 D1 队列写放大、n8n SQLite、纯 JS 转码、图片下载卡顿和缺少 Queue 指标后的上线风险控制值。

### 6.2 接入免费 Cloudflare Queues，但保留 Workers Free

- 如果图片已经是合规 JPG，或者转换已移出 Worker：建议 2,000 张/天，峰值可放到 2,500 张/天。
- 如果仍让 Free Worker 执行当前 PNG 转 JPG：不具备可靠生产能力，不应按图片日额度上线。
- 适合开发环境、内测、小客户和低频批量任务，不适合作为 100～200 持续并发 SaaS。

### 6.3 Workers Paid + Cloudflare Queues

Workers Paid 包含每月 1,000,000 Queue operations，超过后按量计费。单跳且无重试时约为 333,333 条消息/月，折合日均约 11,111 条；保留余量后，可按 8,000～10,000 张图片/天使用包含额度。

付费目标：

| 层级 | 推荐并发 |
|---|---:|
| API/回调入口 | 100～200 以上 |
| 外部 AI 图片工作流在途 | 100～200 |
| metadata consumer | 20～50 |
| R2 流式中继 | 20～50 |
| 纯 Worker 图片转码 | 4～8 |
| 单用户图片在途 | 默认 20 |

## 7. 100～200 并发容量模型

外部 AI 图片工作流耗时为 100～600 秒。按 200 个在途任务计算：

```text
最慢完成速率：200 / 600 = 0.33 张/秒
最快平均完成速率：200 / 100 = 2 张/秒
```

当前单张转码约为秒级，因此只需要约 1～4 个持续转码槽位。配置 4～8 个独立 Queue consumer，就可以吸收正常完成速率并为回调突发保留余量。

结论：系统需要 100～200 个外部工作流槽位，但不需要 100～200 个转码槽位。

如果“100～200 并发”指 100～200 个母任务，且每个母任务包含 9 张以上图片，则实际在途图片工作流可能达到 900～1,800 以上，需要单独扩大 n8n、AI 提供方配额和租户调度上限。

## 8. SaaS 目标架构

```text
Pages
  -> API Worker
       -> D1：任务、额度、幂等状态、聚合计数
       -> workflow-dispatch Queue
             -> n8n main -> Redis -> n8n workers -> AI

n8n/AI
  -> R2 staging（S3 client 或 presigned PUT）
  -> callback Worker
       -> image-callback Queue -> 转码/校验 -> R2 final -> D1
       -> metadata Queue -> D1
```

设计约束：

1. D1 只保存业务状态，不再承担高频图片消息队列。
2. 每个回调只进入一个 Queue，避免 callback queue 再转发 image queue。
3. Queue 消息只传 ID、URL 或 R2 key，不传图片和大 metadata payload。
4. callback Worker 只有在 `queue.send()` 成功后返回 2xx；失败返回 503，让 n8n 重试。
5. 使用 `event_id = plan_id:image_type:image_position:attempt` 做幂等。
6. 图片优先由 n8n/AI 直传 R2 staging，回调只返回 `r2_key`、`etag`、`size` 和 `content_type`。
7. Worker 内部访问 R2 使用原生 binding；n8n 或外部工作流使用 R2 S3 endpoint 或 presigned PUT。
8. S3 客户端不能让 R2 自动抓取任意 HTTP URL；如果 AI 只返回临时 URL，仍需 n8n 或 relay consumer 下载后上传。

官方来源：

- [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)
- [R2 S3-compatible API](https://developers.cloudflare.com/r2/api/s3/api/)
- [R2 Presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)

## 9. 动态调度算法

### 9.1 分层令牌

- 单用户默认 `user_image_inflight = 20`
- 全局初始 `global_image_inflight = 50`
- 经压测逐步提高到 100，再提高到 200
- metadata、图片生成、图片中继和转码使用独立额度

### 9.2 AIMD 动态控制

满足以下条件时，每 30 秒增加 5 个全局图片槽位：

- n8n dispatch p95 正常
- Queue age p95 低于目标
- 最近窗口没有 429
- timeout/error rate 低于阈值

出现 429、超时、D1 错误或 Queue age 持续增长时：

```text
global_limit = max(min_limit, floor(global_limit × 0.7))
```

### 9.3 多租户公平性

使用 weighted fair queue 或 deficit round robin：

- 每轮每个用户最多取得固定数量的 dispatch token
- 套餐只影响权重和用户上限，不允许单租户占满全局资源
- metadata 等快速任务优先于图片慢任务
- 转码消费者设置租户级并发 1～2，避免大任务占满 4～8 个转码槽位

## 10. 实施顺序与验收标准

### 阶段 A：消息层

1. 新增 Cloudflare Queue producer/consumer binding。
2. 图片回调直接进入 image callback Queue，metadata 进入 metadata Queue。
3. 保留 D1 业务状态和幂等索引，停止把 D1 表作为主消费队列。
4. 配置 DLQ、重试和 Queue operation 指标。

### 阶段 B：图片层

1. R2 增加 staging/final key 约定。
2. Queue consumer 设置 `batch_size = 1`、`max_concurrency = 4～8`。
3. 为图片响应体增加 idle 和 total timeout。
4. 对已是 JPG 的图片直接校验和写 R2；只有 Shopee PNG 主图/附图进入转码。

### 阶段 C：n8n

1. SQLite 迁移 PostgreSQL 13+。
2. 增加 Redis，启用 `EXECUTIONS_MODE=queue`。
3. 部署 1 个 main、2 个 worker，每个 worker 先配置 25 并发。
4. 100 并发压测通过后扩到 4 个 worker 或提高单 worker 并发。

### 验收基线

- 200 个图片工作流同时在途 30 分钟
- 200 条 callback 在 60 秒内集中返回
- callback ack p95 小于 500ms
- Queue age p95 小于 30 秒
- 重复 callback 不产生重复图片和重复扣费
- Queue send 失败时 callback 返回 503
- consumer 异常后消息可以重试并最终进入 DLQ
- 不存在超过 900 秒仍无终态的外部图片计划
- 单个转码 invocation 不同时解码多张图片
- 免费版每日 Queue operations 控制在 8,000 以下

---

## 11. 最终建议

1. 免费 Cloudflare Queues 的实际产品额度按 2,000 张生成图片/天发布，2,500 只作为低重试情况下的峰值，不对用户承诺 3,333 理论值。
2. 免费方案必须要求图片已为合规 JPG，或把 PNG 转 JPG 移出 Free Worker。
3. 当前未接入 Cloudflare Queues 前，保持 1,000 张/天保护值和 20～50 个全局在途图片任务，不宣布 100～200 并发 SLA。
4. SaaS 正式版本采用 Workers Paid、Cloudflare Queues、R2 staging/final、D1 业务状态、n8n PostgreSQL + Redis queue mode。
5. 100～200 并发目标先以“图片工作流在途数”验收；转码并发固定从 4 开始，根据 Queue age 和 CPU 指标扩到 8。
